# ADR 017: Post-handshake address exchange

**Status:** Accepted — implementation deferred; ships alongside mDNS in v0.3.0

## Context

The peer table is `HashMap<PeerId, Vec<PeerAnnouncement>>`. `send()` builds candidates
by pairing each known address against each available transport of the matching kind (ADR
016). For fallback to work, the Vec must contain an address for every transport the peer
is reachable on.

Addresses enter the Vec through per-transport discovery: mDNS for QUIC, BLE scan for BLE.
These two discovery paths run independently and at different speeds. mDNS announces a peer
in under a second. BLE discovery requires a scan window, a GATT connect, and a Noise_XX
handshake — typically three to five seconds longer. If a transport failure happens before
the slower path completes, the Vec is incomplete and delivery fails even though the peer
is still reachable on the other transport.

The same incompleteness appears in manual `--peer` mode: `add_peer()` inserts exactly one
QUIC address. BLE may independently discover the peer, but that is not guaranteed to
happen before the first send or before WiFi drops.

ADR 016 gives the routing layer the right shape to handle multiple addresses. It cannot
help if the Vec never gets populated with all of them in time.

## Decision

After every Noise_XX handshake, both sides exchange the list of `PeerAddress` values they
are currently advertising on active transports, before any application payload flows. This
is called the address exchange. On success, both sides upsert the received addresses into
the peer table. The exchange is best-effort: a timeout or parse error causes a debug log
and the session continues normally.

Add `fn local_addresses(&self) -> Vec<PeerAddress>` to the `Transport` trait with a
default implementation that returns an empty Vec. Transport implementations that can
determine their own advertising address implement this method. Those that cannot return
the default.

For v0.3.0: `QuicTransport` implements `local_addresses()` to return its current listen
address. `BleTransport` returns the default empty Vec (see Rationale).

## Wire format

Application message IDs are generated by `new_message_id()`, which sets the high bit of
the first byte (`bytes[0] |= 0x80`). This guarantees that application message IDs have
first byte in the range `0x80`–`0xFF`.

A control message is identified by first byte `0x00`. The full 8-byte control ID is:

```
[0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x01]   address exchange (type 1)
```

Additional control message types may be assigned in future ADRs by incrementing the last
byte. No other bytes in the range `0x00`–`0x7F` for the first byte will be used by
application code, preserving the full space for future control types.

Address exchange payload (follows the 8-byte control ID):

```
[count: u8]                   number of addresses (0 = no addresses to share)
for each address:
  [kind: u8]
    0x00 = QUIC over IPv4
    0x01 = QUIC over IPv6
    0x02 = BLE
  for kind 0x00 (QUIC IPv4):
    [ip:   4 bytes, network byte order]
    [port: 2 bytes, big-endian]
  for kind 0x01 (QUIC IPv6):
    [ip:  16 bytes, network byte order]
    [port: 2 bytes, big-endian]
  for kind 0x02 (BLE):
    [len: u8]                 byte length of the UTF-8 string
    [id:  len bytes]          BLE peripheral ID string (MAC or UUID)
```

BLE peripheral ID strings are platform-specific ASCII: 17 bytes on Linux (MAC format
`AA:BB:CC:DD:EE:FF`), 36 bytes on Windows and macOS (UUID format). Both fit in a `u8`
length prefix. The receiver stores the string as-is into `PeerAddress::Ble(String)`.

The encoding is intentionally simple: no versioning byte, no checksum, no schema. If a
future format change is needed, a new control message type handles it. Unrecognised
control types are silently ignored.

## Protocol flow

### try_connect (initiator — discovery handshake, no application payload)

1. Connect and complete Noise_XX handshake.
2. Send address exchange frame (own addresses).
3. Receive remote's address exchange frame with a 2-second timeout.
   On timeout or parse error: log at debug, skip upsert, continue.
4. Upsert received addresses into the peer table (dedup by address).
5. Close the session.

### try_send (initiator — application payload)

1. Connect and complete Noise_XX handshake.
2. Send address exchange frame (own addresses).
3. Receive remote's address exchange frame with a 2-second timeout.
   On timeout or parse error: log at debug, skip upsert, continue.
4. Upsert received addresses into the peer table.
5. Send application frame: `[msg_id: 8 bytes][payload]`.
6. Receive ACK (empty bytes, per ADR 009).
7. Close the session.

### handle_incoming (responder)

1. Complete Noise_XX handshake.
2. Receive first message.
   - If first byte is `0x00`: it is a control message.
     Parse the address exchange payload, upsert into the peer table, send own address
     exchange frame, then receive the application frame (step 3).
   - Otherwise: the peer does not implement address exchange (old version or timeout).
     Treat the received bytes as the application frame directly (step 3).
3. Process the application frame (dedup check, on_message, ACK).
4. Continue the receive loop for subsequent messages.

The backwards-compatibility branch in step 2 ensures that a node running this version
can still communicate with a node running an older version that does not send an address
exchange frame.

## Rationale

**Why mask new_message_id() rather than use a separate framing layer?**

Adding a type byte to every application frame would change the wire format for all
existing messages and break any deployed nodes mid-upgrade. Masking the high bit of the
message ID reserves a range of IDs as control space without touching the application frame
structure. The deduplication cache (ADR 011) still operates on the full 8-byte ID; the
effective application ID space is 2^63 values, which is sufficient.

**Why a 2-second timeout on the exchange receive?**

Long enough to survive a BLE GATT round-trip on a busy channel. Short enough that a
stale peer or a version mismatch does not add perceptible latency to every send. The
session never blocks application traffic past this point regardless of what the remote
does.

**Why is the exchange safe to repeat on every connection?**

The upsert step checks for address equality before pushing to the Vec (consistent with
ADR 016's approach for `connect()` and `add_peer()`). Receiving the same address on
every connection is harmless: the Vec stays bounded and the routing path is unchanged.

**Why does BleTransport return an empty Vec from local_addresses()?**

A BLE peripheral does not observe its own advertising address the same way a scanning
central observes a remote device's address. The address that other devices see when they
scan for us is assigned by the BLE adapter and varies by platform: MAC address on Linux,
UUID on Windows and macOS, randomised UUID on macOS for privacy. Retrieving it reliably
requires platform-specific adapter queries that are out of scope for v0.3.0.

The consequence: a QUIC connection does not learn the peer's BLE address through the
exchange in this release. BLE addresses are still populated by BLE peer_stream. The
exchange is still useful in the reverse direction: a BLE connection does learn the peer's
QUIC address. Full cross-transport address exchange, where every connection type reveals
all address types in both directions, requires BleTransport implementing
`local_addresses()` and is deferred to a follow-up once adapter address retrieval is
confirmed stable on Linux and Windows.

**Why defer implementation until mDNS is in place?**

The timing race this fix addresses (one transport's discovery completes quickly, another
takes seconds longer) only manifests at scale once mDNS is implemented. Without mDNS,
QUIC peers are added manually via `--peer` and there is no fast-path discovery to race
against. Implementing the exchange before mDNS lands means QUIC connections share only
QUIC addresses (already known to both sides via `--peer`), and BLE connections share
nothing (BleTransport returns empty). The exchange would be a no-op in practice.
Deferring ensures the protocol is exercised against real timing races from the moment it
lands.

## Implications

- `Transport` trait gains `fn local_addresses(&self) -> Vec<PeerAddress>` with a default
  empty implementation. No existing transport implementation breaks.
- `new_message_id()` gains the `bytes[0] |= 0x80` mask. The application ID space shrinks
  from 2^64 to 2^63 values, which remains sufficient for deduplication.
- `try_connect` and `try_send` gain the exchange send and receive steps. Round-trip count
  per send increases by one. On a local network this adds one BLE GATT or QUIC
  round-trip of latency per message. This is acceptable for v0.3.0 and can be pipelined
  if latency becomes a concern.
- `handle_incoming` gains a control-message branch before the application receive loop.
  The first recv is pulled out of the loop to inspect the message type.
- `accept_loop` must pass the peer table reference and local addresses to
  `handle_incoming`. The `Router` exposes a `local_addresses()` method that aggregates
  across all registered transports.
- Issue #70 is closed when this ADR's implementation ships in v0.3.0.
